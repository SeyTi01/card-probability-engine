# Release notes

Read the actual changes between the relevant previous published package tag and intended release commit. Verify tags and exclude reverted work. Notes describe benefits to library consumers: supported semantics, accuracy, API compatibility, resource behavior and measured performance.

Use one to three short bullets, usually under 60 words. Preserve required migration/API/model-version guidance even when it needs a separate paragraph. Do not inventory internal refactors, routine tests, CI or plugin work; do not infer a speed or accuracy gain.

Remove the weakest bullet unless it carries a meaningful benefit or required action. Append a comparison link only when both tags exist. For publication, link the exact package, accepted candidate and rehearsal record. Publish curated text without generated-note inventories.
